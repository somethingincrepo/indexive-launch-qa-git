<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Website publishing verification means comparing the copy and URL you approved against what the public page actually delivers. The working sequence is to capture a baseline, publish, read the public page back, record a pass, fail or unknown for each check, and keep a rollback path ready.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The reason to do this is that a content system can show the right text while the public page shows something else. Sanity, for example, stores drafts and published content as separate documents, so a correct editor view can sit beside a different public page. Prepared by the Indexive QA editorial team, dated 2026-11-03.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What does website publishing verification confirm?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Verification confirms that three things agree: the approved copy, the expected public URL and the page a visitor actually receives. You write down what should be true before you publish, then observe the public page afterward and compare the two.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The workflow has four beats: baseline, change, publish and public verification. A baseline copied from the same live state after publishing does not independently establish the intended revision. Preserve the approved copy separately so it can be compared with the public result. The public readback is the observation that gets measured against the baseline, which stays fixed as the reference.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A note on the examples. Every business, person, option and worksheet used as a scenario here belongs to the fictional Northstar Demo Lab, whose definitions are dated 2026-11-02. They are authored test material, not real customers, offers or results, and no purchase or contact submission exists behind them. The technical statements are different. The technical statements come from Google, MDN, W3C and Sanity documentation, and each one names its source where it appears.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What do you get from doing this? You get a record of what you checked, what passed, what failed and what you could not finish. That record is what lets you decide whether to leave a page live or put the previous version back.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>How do you capture an approved baseline before publishing?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Record the expected copy and the expected public URL before anything goes live. That is the purpose of the fictional Baseline Capture worksheet concept in the Northstar scenario, which records exactly those two things. The worksheet specifies what to write down and is not a downloadable product. Our fictional page, <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-baseline-capture">Publishing Review Baseline Capture: Copy and Canonical URL</a>, is the labelled scenario reference for it.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>In the scenario, an editor called Casey starts from a draft baseline, selects the expected public URL and then runs a checklist. Casey is a fictional persona and does not stand for a real customer or a byline. The useful part is the order: the expected URL is chosen before the checks begin, so nobody picks the URL that happens to match what they find.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A practical baseline goes beyond body text. Capture the values you will want to compare later:</p>
<ul style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>
<li>The approved body copy, including headings.</li>
<li>The page title and meta description you intend to ship.</li>
<li>The canonical URL you want declared.</li>
<li>Any structured data values, such as the page type and the name or description it states.</li>
<li>The expected public URL itself, written out in full.</li>
</ul>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Each recorded value turns a vague question like "does this look right?" into a concrete one: does the live value equal the recorded value? Without a baseline, the only thing you can compare the live page to is your memory.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Why is a correct CMS view not proof the public page is right?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A correct view in your content system does not prove the public page is right, because the editor view and the public page are separate observations. Sanity's documentation says drafts have a drafts. ID prefix, while published documents have no such prefix, and the published perspective excludes unpublished changes (<a href="https://www.sanity.io/docs/content-lake/drafts-and-versions">Sanity drafts and versions documentation</a>). So the document you see while editing may not be the one the public sees.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Sanity also distinguishes perspectives. The drafts perspective applies drafts for preview, and the published perspective returns only published content. A preview therefore tells you what a draft-applying query returns. It says nothing about what the public renderer is serving. The same documentation notes that a frontend using the published perspective excludes draft-only edits, and warns that you must not assume an unknown frontend query or delivery configuration uses the published perspective.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Timestamps and text are weaker evidence than they seem. According to Sanity, the published document stays intact while a draft is edited, until publication, but direct writes to the published document can also change it. That means current document text or an updatedAt value alone does not prove that publication never happened, and it does not prove it did.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>This yields three states to keep apart: the draft, the published document and the public page. Our reference page, <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-published-document">Sanity Published Document and Public QA Renderer</a>, links the Sanity documentation and distinguishes published-perspective document state from a separate public renderer observation. The technical authority here is Sanity's own documentation. You record the public observation in a separate step, which our fictional <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-public-readback">Publishing Review Public Readback: Published Copy and Canonical URL</a> worksheet exists to illustrate.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Is an HTTP 200 enough to say a page was published correctly?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>No. MDN describes HTTP 200 as indicating that the request succeeded (<a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/200">MDN HTTP 200 reference</a>). A response status alone does not compare the delivered copy with an approved draft. Even with a 200 response, a page can carry yesterday's headline, a missing paragraph or the wrong title.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The status code is one row in the checklist. It tells you the server answered the request successfully. The code leaves open whether the body copy, title and metadata match your baseline. Readback therefore has to compare those against the baseline directly: read the heading text, the body text, the title element and the description, and check each against the recorded value.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>There is some supporting evidence for recording more than a status. In a controlled run, we put 17 deterministic synthetic page-type fixtures through a registered implementation worker, an isolated migrated database and a disposable GitHub repository. Every fixture had persisted verification. These were software tests, not customers and not production traffic, so the run says nothing about how often real publishes fail.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What should you check in the title, metadata and structured data?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Check that the live title element, description and structured data equal the values in your baseline and still describe the visible page sensibly. Google recommends title elements that are distinct, descriptive, concise and accurate about the page content (<a href="https://developers.google.com/search/docs/appearance/title-link">Google title link documentation</a>). A readback should therefore ask two questions: does the title equal the approved title, and does it still describe the page?</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Structured data needs the same two-part check. Google explains that structured data supplies explicit information about the meaning and content of a page, and recommends choosing markup that represents the visible page content (<a href="https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data">Google structured data introduction</a>). Markup can be syntactically valid and still describe content the page no longer shows, for instance a name or description left over from an earlier version. Validity is not the same as agreement with the page.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Our fictional <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/guide">Northstar demo guide</a> gives a concrete thing to read back. It is a real disposable demonstration page, explicitly fictional, and it contains a title, a description, a canonical value and WebPage JSON-LD. Reading those four values from the public HTML and setting them beside the baseline is the whole exercise. Nothing about that page establishes commercial outcomes; it is only an example of values you can compare.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>How do canonical URLs and redirects differ, and which do you verify?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A canonical URL is a declared preference for search deduplication, while a 301 is a server response that sends the browser elsewhere. Verify both, separately. Google explains that canonicalization selects a representative URL for duplicate content, and a site owner can indicate a preferred URL, though that preference and Google's selection are distinct (<a href="https://developers.google.com/search/docs/crawling-indexing/canonicalization">Google canonicalization documentation</a>). Canonicalization is a search process and gives a browser no instruction to navigate anywhere.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A redirect does act on the browser. MDN says an HTTP 301 means the requested resource has moved permanently, with a Location header naming the destination, and a browser receiving it requests that destination (<a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/301">MDN HTTP 301 reference</a>). The same source is clear that no redirect behavior should be inferred from a canonical link alone. A page can declare a canonical URL and still be served at the address you requested.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Signals should also agree with one another. Google treats rel=canonical and redirects as strong canonicalization signals and sitemap inclusion as a weaker one, and says canonical preferences should be consistent (<a href="https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls">Google guidance on consolidating duplicate URLs</a>). If your canonical tag names one URL, a redirect sends visitors to another and your sitemap lists a third, you have sent conflicting preferences.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>In practice, check two things on the public page. First, read the declared canonical value and compare it with the expected public URL from your baseline. Second, request the URL and note the actual response: whether it returns 200 directly or a 301 with a Location header. Record both as separate results. Our fictional public readback worksheet concept is the place to log the observed response and content.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>How do you verify a noindex page?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Read back the noindex directive on the public page, then confirm that robots.txt does not stop crawlers from reaching it. Google says a noindex meta tag or response header can prevent indexing when the crawler can access the page, while blocking crawling in robots.txt prevents Google from seeing the rule (<a href="https://developers.google.com/search/docs/crawling-indexing/block-indexing">Google documentation on blocking indexing</a>). A noindex that Google cannot fetch is a noindex Google never reads.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>That gives a two-part check. The first part is the directive itself, either a robots meta tag in the HTML or a header on the response. The second is access: if a robots.txt rule blocks the URL, the page may carry the right tag and still be unable to deliver the message. Checking only one half can produce a false pass.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The Northstar demo guide is intentionally noindex,nofollow, so a readback of that page can confirm the directive together with its title, description, canonical and JSON-LD. Be careful about what that proves. It confirms what the public HTML says. It is not proof of what any search engine has indexed, and this guide makes no claim about search results.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What does a preliminary accessibility check prove?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>It proves that you looked at a short list of obvious problems, not that the page is accessible. W3C's Easy Checks cover preliminary checks including page titles, alternative text, headings, contrast and keyboard access, and passing them is not comprehensive accessibility conformance proof (<a href="https://www.w3.org/WAI/test-evaluate/preliminary/">W3C preliminary checks</a>).</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>That still makes them useful at publishing time. A heading that disappeared, an image that lost its alternative text or a control you can no longer reach with the keyboard are the kinds of changes a publish can introduce, and a quick pass catches some of them. Record the result as a preliminary check and word it that way.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The fictional Northstar scenario, dated 2026-11-02, shows the right framing. Its invented Extended review option lists preliminary keyboard, heading and image checks and states plainly that it does not certify WCAG conformance. WCAG is the W3C's Web Content Accessibility Guidelines. The <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-demo-catalogue">fictional Demo Review Catalogue: Basic, Extended and Team</a> page is a labelled reference for how such a scope statement reads. It is authored test data, not a real offer.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>How do you sign off, and what do you do with a check you could not finish?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Record pass, fail or unknown for every item, and send unresolved ones to the person responsible for them. In the fictional scenario, Casey does exactly that: runs the checklist, records one of the three results and refers unresolved issues to a responsible reviewer. Unknown is more honest than a forced pass, because a pass you did not earn hides the gap from the next person.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Sign-off comes after the observation, not before. The Public Readback worksheet concept records the observed response and content, and the decision is made from that record. The table below pulls the checks from this guide into one place.</p>

<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A few rules keep the table honest. Use unknown when you could not run the check, for instance because the page was unreachable or you lacked access to the response headers. Use fail when you observed a mismatch. Use pass only when you compared the live value with the recorded one and they agreed.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What does a full verification run look like, including retries and rollback?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A full run follows baseline, change, publish and public verification, and ends with either a signed-off page or a rollback that has itself been verified. The Northstar demo guide states that same workflow. After publishing, you read the public page back and fill in the checklist. If every item passes, you sign off. If something fails and cannot be fixed quickly, you roll back.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Our synthetic experiment exercised this loop. Each of the 17 deterministic fixtures had persisted verification, then a duplicate retry that produced no change in the provider SHA (the commit identifier from the repository host), and then a rollback ending with file absence and a public 404. In that run, the duplicate retry came with no provider SHA change. The limits matter just as much. These were synthetic software tests in a disposable setup, not customers, not production, and not proof of search indexing or accessibility. A sample of 17 cannot establish general failure rates, and we make no such claim.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>For the rollback decision itself, the fictional Rollback Decision worksheet concept records three things: a reason, the prior revision and a post-restore check. The labelled scenario page <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-rollback-decision">Publishing Review Rollback Decision: Prior Copy and Canonical URL</a> is the reference for it. The reason says why you are reverting. The prior revision says exactly what you are restoring. The post-restore check says how you will confirm the restore worked.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Keep the post-restore check in the record. A rollback is unverified until the post-restore public check is done. Restoring the prior revision in your content system is a change to the document state, and the public page is a separate observation, so you read the public page back again and compare it with the prior baseline, just as you did after the original publish.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Frequently asked questions</h2>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Does a CMS preview prove the public page is correct?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>No. Sanity's drafts perspective applies drafts for preview, while the published perspective excludes unpublished changes. A preview shows what a draft-applying query returns, so you still need a separate readback of the public page.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Does an HTTP 200 prove the page was published correctly?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>No. According to MDN, 200 indicates the request succeeded. It does not compare the delivered copy with the approved draft, so you must check the body, title and metadata against your baseline.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What is the difference between a canonical link and a 301?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A canonical declaration states a preferred URL for search deduplication, and Google's choice can differ from the owner's preference. A 301 is a permanent move with a Location header, which a browser follows. MDN notes that no redirect should be inferred from a canonical link alone.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Why might a noindex rule be ignored?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Google says a noindex tag or header can prevent indexing when the crawler can access the page. If robots.txt blocks crawling, Google cannot see the rule. Check both the directive and crawler access.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What does passing W3C Easy Checks prove?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>It shows that a set of preliminary checks passed, covering page titles, alternative text, headings, contrast and keyboard access. W3C states that this is not comprehensive accessibility conformance proof. Record it as a preliminary result only.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What should a rollback record include?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>In the fictional Northstar worksheet concept, a rollback record holds a reason, the prior revision and a post-restore check. Until that public check is done, the rollback is unverified. Read the public page back after restoring and compare it with the earlier baseline.</p>

<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A page that returns a 200 response can still show old copy, because the status only tells you the request worked. Before you touch anything, work out whether you are on the wrong URL, looking at a change that exists only as a draft, or receiving a stale delivered copy, and run one check for each.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>By the Indexive QA editorial team (test attribution, no individual credentials). Dated 2026-11-03. The scenario material here, including the persona and worksheets, is fictional and was defined on 2026-11-02. It describes no real customers or incidents.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What the symptom tells you and what it does not</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>You published, you reloaded, and the old text is still there. The tempting conclusion is that something is cached. Hold that thought for now. None of the sources we rely on explain how caching behaves, so we treat it as a hypothesis to test last.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Start with what the response can and cannot tell you. According to MDN, <a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/200">HTTP 200 indicates request success</a>. A status alone does not compare the delivered copy with an approved draft, so a 200 cannot tell you whether the copy you see is the copy you approved.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Three explanations are worth separating: the wrong URL, a draft-only state, and a stale delivered copy. Each gets its own check below, and none gets blamed until its check has been run.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>It helps to ask what each explanation would predict. A wrong URL predicts that the address you ended up on differs from the one you meant to check, and a redirect, if there is one, will show in the response headers. A draft-only state means the intended edit is present in the draft but is not present in the current published document; this does not establish its publication history. A stale delivered copy predicts that the published document already matches your approved text while what the public page returns does not. Use these observations to narrow the possibilities. A mismatch alone does not establish the cause; record unknown when the available checks do not resolve it.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The order matters too. If you start with the explanation you find most likely, you may overlook a relevant observation. Start with the checks that need only a browser and a header readout, then move to the ones that need access to the content store or to the frontend's configuration.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Record what you expected before you check anything</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Use the fictional <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-baseline-capture">Baseline Capture specification</a> to record the expected copy and public URL first. Then record what you actually observe, the response and the content, next to it. Without that baseline you cannot tell a failed check from one you never completed.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Log every check as pass, fail or unknown. Mark any cause you could not verify as unknown, which is a legitimate result.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A useful record has four parts: the expected copy, the expected public URL, the observed response (the status and, for a redirect, the Location header), and the observed content. Keep the wording of the expected copy exact, since a vague note like "the new intro" can't be compared with anything. Date each entry so a later reader knows which observation came first.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The record also helps you keep checks apart. If you see the old text, then check again later and see the new text, the log shows which checks were run in which state, so you can tell whether something changed or you simply looked at a different state of the page.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Casey, a fictional editor persona, works this way: take a draft baseline, pick the expected public URL, run the checklist, record pass, fail or unknown, and refer anything unresolved to a responsible reviewer. The fictional worksheet concepts follow the same split. Publishing Review Baseline Capture: Copy and Canonical URL records expected copy and URL, and <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-public-readback">Publishing Review Public Readback: Published Copy and Canonical URL</a> records the observed response and content. Both are labelled fictional specifications.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Likely causes of old content on a published page</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Work in this order, from the cheapest check to the one you can least verify: wrong URL, then draft-only state, then the frontend's configuration, then a stale delivered copy.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>You may be looking at the wrong URL</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Check the status and the Location header, then compare the final URL with the expected public URL. MDN defines a 301 as a permanent move: <a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/301">the Location header identifies the destination, and the browser requests it</a>. If you typed one address and landed on another, a redirect may be the reason, and the header will show it.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A canonical link is a different thing. Google describes canonicalization as <a href="https://developers.google.com/search/docs/crawling-indexing/canonicalization">a search deduplication process</a>, which gives a browser no instruction to navigate elsewhere. A canonical link alone implies no redirect, and the preferred URL you declare can differ from the one Google selects.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Google also treats <a href="https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls">rel=canonical and redirects as strong signals, with sitemap inclusion weaker</a>, so keep your preferences consistent. If the final URL differs from the expected one, confirm the redirect header before drawing any conclusion.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The change may exist only as a draft</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>In Sanity, <a href="https://www.sanity.io/docs/content-lake/drafts-and-versions">drafts have a drafts. ID prefix and published documents do not</a>. Draft edits leave the published document untouched until publication, and the published perspective excludes unpublished changes. If your edit lives only under the drafts. ID, the published document still holds the old copy, so a public page reading the published perspective would show it.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>To check, compare the draft and published documents by ID and read the document through the published perspective. Don't lean on timestamps. Sanity's documentation says that <a href="https://www.sanity.io/docs/content-lake/drafts-and-versions">current document text or updatedAt alone does not prove that publication never occurred</a>, because direct writes can also change the published document. Our navigation page on the <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-published-document">Sanity Published Document and Public QA Renderer</a> separates document state from what the public renderer shows.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The frontend may not read the published perspective</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The published perspective excludes draft-only edits, while the drafts perspective applies drafts for preview. If the public site queries with a different perspective than you assume, you may be comparing different document states, so confirm the perspective before drawing a conclusion.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Check which perspective the frontend actually requests. Don't assume it is the published one: per Sanity's documentation, an unknown frontend query or delivery configuration <a href="https://www.sanity.io/docs/content-lake/drafts-and-versions">must not be assumed to use the published perspective</a>. We don't cover framework specifics here because the configuration is unknown.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A stale delivered copy is a hypothesis to test last</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Cache is a hypothesis here, not an explained mechanism, since no source we rely on describes how it works. It becomes plausible only when the wrong URL and draft-only state are excluded, and the published document matches your baseline while the delivered content does not.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The check is to compare the delivered copy with the baseline. If you cannot verify the result, leave it unknown and hand it on.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Keep indexing signals separate. Google says a <a href="https://developers.google.com/search/docs/crawling-indexing/block-indexing">noindex tag or header can prevent indexing, and blocking crawling in robots.txt prevents Google from seeing that rule</a>. Those concern search results, not what a visitor sees in a browser, so don't treat them as the cause of old copy.</p>

<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Frequently asked questions</h2>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Does HTTP 200 mean the page is current?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>No. It means the request succeeded. The status says nothing about whether the delivered copy matches your approved draft, so compare the content against your baseline.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What is the drafts. prefix?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>It is the ID prefix Sanity gives draft documents. Published documents have no such prefix. Draft edits don't change the published document until you publish.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Is a canonical tag a redirect?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>No. A canonical link signals a preferred URL to search and implies no redirect. A 301 response redirects the browser to its Location destination.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Does noindex change what visitors see?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Nothing in our sources says it does. It concerns Google indexing. If robots.txt blocks crawling, Google cannot see the noindex rule at all.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Does updatedAt prove the change was published?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>No. Sanity's documentation says text or updatedAt alone does not prove publication never occurred, and direct writes can change published documents. Compare the draft and published documents by ID instead.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>When should I escalate or roll back?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Escalate when checks leave the cause unknown. Consider rollback when wrong copy is live and a prior revision exists. Record the reason and check the public page afterwards. For the labelled demonstration workflow, inspect the <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/guide">public QA guide</a>.</p>

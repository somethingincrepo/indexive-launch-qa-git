<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Review one low-risk page yourself with a checklist, and move to a scoped review when you have several pages, structured data, indexing or rollback records to check. This article is by the Indexive QA editorial team, dated 2026-11-03, and it compares options from a fictional scenario, so every Northstar Demo Lab option, price and persona below is illustrative and not a real offer.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>We are the author of those scenario options, so treat them as one set of examples rather than a ranking. The scenario definitions are dated 2026-11-02. Casey, a fictional editor, compares an approved draft with the public URL and records pass, fail or unknown. That habit is the core of any review approach.</p>

<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The table shows what each option covers. Self-managed review costs no assigned fee but puts all the effort on you: you supply the time, the expertise and a record of what you observed. Basic, Extended and Team each add a defined set of checks per exercise, and each lists exclusions. Basic excludes code changes, accessibility certification, ranking guarantees and recurring monitoring. Extended excludes WCAG conformance certification and production fixes. Team has the Extended checklist and adds no further technical guarantees. Team adds coordination only, so its extra cost buys a shared sign-off sheet and two reviewer roles rather than deeper technical checking. Read the exclusions column as closely as the inclusions, so you do not choose an option on the assumption that it covers something it explicitly leaves out.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Why a page can return HTTP 200 and still be wrong</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>An HTTP 200 only indicates request success. A response status alone does not compare the delivered copy with an approved draft, as <a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/200">MDN's documentation on the 200 status</a> explains. Even a cleanly loading page may carry an old headline or the wrong title.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Two steps catch this. Baseline Capture records the expected copy and URL, and Public Readback records the observed response and content, as the fictional worksheets are specified. See <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-baseline-capture">our baseline capture worksheet for copy and canonical URL</a> and <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-public-readback">our public readback worksheet for published copy</a>. Both are fictional specifications.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Basic includes a title comparison and public URL check. Google recommends <a href="https://developers.google.com/search/docs/appearance/title-link">distinct, descriptive, concise title elements that accurately describe page content</a>, so the title is a sensible first thing to compare.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Does the CMS showing the right text prove the public page matches?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>No. In Sanity, drafts have a drafts. ID prefix and published documents do not. The published perspective excludes unpublished changes, and later draft edits do not alter the published document until publication <a href="https://www.sanity.io/docs/content-lake/drafts-and-versions">according to Sanity's documentation</a>.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Direct writes to the published document can also change it, so current text or an updatedAt value alone does not prove that publication never occurred <a href="https://www.sanity.io/docs/content-lake/drafts-and-versions">Sanity documentation</a>. A frontend using the published perspective excludes draft-only edits, but you shouldn't assume an unknown frontend query or delivery configuration does. Observe the public page separately from document state.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Criteria that change which option you need</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Self-managed review can handle title and copy checks. The criteria below are where Extended-style checks start to earn their keep.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Structured data and visible content</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Structured data gives explicit information about a page's meaning, and Google advises choosing <a href="https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data">markup that represents the visible page content</a>. Checking JSON-LD means comparing it with what readers see. Extended includes this consistency check.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Canonical, noindex and crawl access</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Google treats rel=canonical and redirects as strong canonical signals and sitemap inclusion as weaker, and preferences should be consistent <a href="https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls">per Google's documentation</a>. A noindex rule works only if the crawler can reach the page; blocking crawling in robots.txt <a href="https://developers.google.com/search/docs/crawling-indexing/block-indexing">prevents Google from seeing that rule</a>. Extended includes canonical and indexability checks.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Preliminary accessibility checks, such as the W3C Easy Checks, cover titles, alternative text, headings, contrast and keyboard access, but passing them is <a href="https://www.w3.org/WAI/test-evaluate/preliminary/">not comprehensive conformance proof</a>.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What Team adds over Extended</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Team runs the Extended checklist across ten pages and adds a shared sign-off sheet and two reviewer roles. The extra cost buys coordination, not additional technical guarantees. Once several people must agree on ten pages, a shared sheet becomes useful.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The technical checks are the same as Extended: JSON-LD consistency with visible content, canonical and indexability checks, preliminary keyboard, heading and image checks, and a rollback decision log. In the scenario, the illustrative price rises from USD149 for three pages to USD299 for ten pages, and the difference pays for scale and sign-off structure. The scenario gives Team the Extended checklist and no additional technical guarantees; it does not separately list all of Team's exclusions. If your pages are few and one person owns the decision, Extended lists the same checks. When several people need to agree before a page is treated as correct, the shared sheet gives them one place to record that agreement.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What to do when a check cannot be resolved</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Casey, our fictional editor, records pass, fail or unknown instead of forcing a binary, then refers unresolved items to a responsible reviewer. Basic's written exception list serves the same purpose. Recording an unknown keeps the gap visible instead of hiding it behind a guessed pass.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The workflow in the scenario runs in order. Casey starts from a draft baseline, selects the expected public URL, runs the checklist, records each result and refers anything unresolved. Casey is a fictional persona. The useful habit is that an unknown is a result in its own right. For example, if you cannot tell whether a frontend uses the published perspective, the honest entry is unknown, followed by observing the public page directly. That keeps the record truthful and tells the next reviewer exactly where to look.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Rollback decisions and confirming the restore</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The Rollback Decision worksheet records a reason, a prior revision and a post-restore check; Extended includes a rollback decision log. See <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-rollback-decision">Publishing Review Rollback Decision: Prior Copy and Canonical URL</a>, a fictional specification.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>In a controlled run of 17 synthetic fixtures, each rolled back with file absence and a public 404. Those were software tests, not customers, and they offer no production, indexing or failure-rate evidence.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The point for a reviewer is that a restore needs its own confirmation. With a reason, a prior revision and a post-restore check on the Rollback Decision worksheet, the record shows why you reverted, what you reverted to and how you confirmed the result on the public page. In that run, the observed result was a public 404 alongside file absence. Extended includes the rollback decision log, while Basic lists no rollback log, so with Basic or self-managed review you would keep that record yourself.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Duplicate retries are worth a mention too. In the same controlled run, each fixture also had a duplicate retry without a provider SHA change. That is a narrow observation from 17 synthetic tests, and it says nothing about how your own system behaves, so check retries on your own pages before relying on them.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A practical way to use this is to decide before publishing who can order a rollback and which prior revision counts as the known good copy. Then the restore is a recorded step with an expected public result, not an improvised fix. Because a status code alone doesn't compare copy with an approved draft, the post-restore check should compare the public page with the prior copy, not just confirm that the URL responds.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Questions to ask and common mistakes</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Ask how many pages you have, who signs off, whether rollback is likely and what each option excludes.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>It also helps to ask what record you will have afterward. A review is only useful later if it shows what was expected, what was observed and what was left unknown. Whichever option you pick, make sure that record exists and that a second person could read it without asking you what you meant.</p>
<ul style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>
<li>Treating HTTP 200 as proof the copy is right.</li>
<li>Trusting CMS state without observing the public page.</li>
<li>Reading preliminary accessibility checks as conformance.</li>
<li>Buying Team for coordination you don't need.</li>
<li>Assuming an option includes an unstated fix or guarantee. Basic excludes ranking guarantees, and Extended excludes production fixes; read each definition separately.</li>
</ul>

<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Frequently asked questions</h2>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What should a website publishing review check after publication?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Compare the public page with the approved draft: copy, title, canonical URL and indexability, structured data against visible content, and preliminary accessibility checks. A status code alone won't tell you any of this.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Is a self-managed publishing checklist enough for a single page?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Often, for a low-risk page, if you have the time and expertise and keep a record of observations. If you need a written exception list or structured data checks, a scoped option in the scenario covers more.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>How many pages justify a coordinated review with sign-off?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>In the scenario, Team covers ten pages with a shared sign-off sheet and two reviewer roles. It adds review coordination, not additional technical guarantees.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What is the difference between a draft baseline and a public readback?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A baseline records the expected copy and URL before publication. The public readback, by contrast, captures the response and content actually observed afterward. Comparing the two reveals mismatches.</p>

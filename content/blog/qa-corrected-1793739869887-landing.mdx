<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>How the review workflow checks a published page</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The fictional editor persona Casey captures a draft baseline, picks the expected public URL, runs a checklist and records each item as pass, fail or unknown. Anything unresolved goes to a responsible reviewer. Casey is a fictional persona and appears here as neither a customer nor a byline.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Two worksheet concepts carry the record. Baseline Capture notes the expected copy and URL, and Public Readback notes the observed response and content. Our fictional pages for <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-baseline-capture">Publishing Review Baseline Capture: Copy and Canonical URL</a> and <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-public-readback">Publishing Review Public Readback: Published Copy and Canonical URL</a> are labelled fictional worksheet specifications.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Why an HTTP 200 response is not enough</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>MDN documents that <a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/200">HTTP 200 indicates request success</a>, and a status alone does not compare delivered copy with an approved draft. That comparison needs the baseline and a readback.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Other checks are separate too. Google recommends <a href="https://developers.google.com/search/docs/appearance/title-link">distinct, descriptive, concise page titles</a>, and its documentation says <a href="https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data">structured data should represent the visible page content</a>. A status code reports none of these, so titles and markup need their own checks.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Draft versus published state in Sanity</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Per <a href="https://www.sanity.io/docs/content-lake/drafts-and-versions">Sanity's drafts and versions documentation</a>, drafts carry a drafts. ID prefix and published documents do not. The published perspective excludes unpublished changes, and the drafts perspective applies drafts for preview. Draft edits leave the published document intact until publication, though direct writes can also change it.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>So an old updatedAt or unchanged text alone does not prove publication never happened. When a frontend's query or delivery configuration is unknown, you can't assume how it behaves. Don't assume a frontend's query or delivery configuration when it's unknown.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Canonical, noindex and robots.txt checks</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Google explains that a noindex tag or header can keep a page out of the index only when the crawler can reach it; <a href="https://developers.google.com/search/docs/crawling-indexing/block-indexing">blocking crawling in robots.txt prevents Google from seeing that rule</a>. If robots.txt blocks crawling, Google cannot see the noindex rule. The demonstration page is intentionally noindex,nofollow.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>For canonicals, Google says <a href="https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls">rel=canonical and redirects are strong signals while sitemaps are weaker</a>, and preferences should be consistent. That keeps the expected URL unambiguous.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What a rollback decision records</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A Rollback Decision worksheet records a reason, a prior revision and a post-restore check. See <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-rollback-decision">Publishing Review Rollback Decision: Prior Copy and Canonical URL</a>, a fictional worksheet specification. In our 17-fixture run, every synthetic fixture also showed rollback with file absence and a public 404.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What the 17-fixture run showed and what it did not</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>We ran 17 deterministic synthetic page-type fixtures. Each showed persisted verification, a duplicate retry without a provider SHA change, and rollback with file absence and public 404. The fixtures were software tests, not 17 customers or 17 AI-written articles, and do not constitute production-worker proof.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The run can't establish general failure rates or prove search indexing or accessibility. It used a registered implementation worker, an isolated migrated database and a disposable GitHub repository, so it says nothing about production workers. W3C's Easy Checks are <a href="https://www.w3.org/WAI/test-evaluate/preliminary/">preliminary and not comprehensive accessibility conformance proof</a>.</p>

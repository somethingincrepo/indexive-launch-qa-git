<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>An HTTP 200 response tells you the request succeeded, and nothing more. It does not tell you the page shows the title and body you approved, because a response status alone does not compare the delivered copy with an approved draft, as <a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/200">MDN's documentation for HTTP 200</a> explains.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>By the Indexive QA editorial team, 2026-11-03. The people and worksheets described here are fictional scenario definitions written for a QA demonstration (dated 2026-11-02). They are not customers, experts, real offers or products.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What does an HTTP 200 response actually tell you?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Think of 200 as a precondition check. The server received the request and served something. Whether that something is the right title and the right body is a separate question the status cannot answer.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The distinction matters most right after a release, when people tend to glance at a status and move on. A status tells you the request succeeded. It does not say which version of the copy was delivered, so a reviewer who stops at 200 has verified the transport and nothing about the content. The title and body need their own comparison against the approved draft.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Take Casey, a fictional editor. Casey opens a page after a release and sees a 200, yet the title still carries last week's copy. The request worked, and the delivered copy was never compared with the approved draft.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>So a 200 verifies one thing: the request was served. It does not verify that the title is right, that the body matches the baseline, or that the edit you made is the one visitors see.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>How can a page return 200 and still show the wrong copy?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>In a CMS with drafts, the copy you edit and the copy the public sees can be different documents. <a href="https://www.sanity.io/docs/content-lake/drafts-and-versions">Sanity's drafts and versions documentation</a> says drafts carry a drafts. ID prefix while published documents have none. The published perspective excludes unpublished changes, and later draft edits do not alter the published document until publication.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Here is a hypothetical, fictional example. Casey rewrites a headline in the draft but never publishes it. The public page keeps serving the published document, so it returns 200 with the older headline. Preview, which uses the drafts perspective to apply drafts, shows the new headline and looks correct. A correct-looking preview therefore does not show what the public frontend serves.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>There's one more caution. If you don't know how the frontend queries content, record that as unknown. Don't assume it uses the published perspective. For the draft-versus-live topic, see <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-published-document">Sanity Published Document and Public QA Renderer</a>, a labelled navigation reference rather than independent technical authority.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Can document text or updatedAt show whether publication happened?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Not reliably. According to <a href="https://www.sanity.io/docs/content-lake/drafts-and-versions">Sanity's documentation</a>, drafts, versions and published content are separate documents, and direct writes to the published document can change it without a normal publish step. So current text or an updatedAt value alone does not prove that publication never occurred, and it can't settle whether it did.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The dependable observation is the public response itself, recorded separately from the state of the document. Look at what the public URL actually returns, then note the document state as context.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Keeping the two records apart avoids a common mistake. If the document text looks right, it is tempting to conclude the public page must be right too. A document that looks wrong tempts you to conclude nobody published. Neither conclusion follows, because the published document can change through a direct write, and a draft edit leaves the published document unchanged until publication. Record what you saw at the URL first, and treat the document state as supporting context.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>How do a 301 and a canonical declaration differ from a 200?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Per <a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/301">MDN's documentation for HTTP 301</a>, a 301 means the requested resource has moved permanently. The Location header identifies the destination, and a browser receiving the response requests that destination. A 200, by contrast, serves content at the URL you asked for.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A canonical link is something else: a page declaring a preferred URL. No redirect behavior should be inferred from a canonical link alone. When you judge a page, first note which URL finally answered and with which status, then read its content.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Here is a fictional example. Casey requests a URL and observes a 301 with a Location header naming a different address. The browser then requests that destination. Casey should check the title and body at the final URL, since the first URL no longer answers with the content. Reading content before noting the redirect risks comparing the baseline with the wrong page.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>How do you check a page title and body against an approved baseline?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A minimal, repeatable check has two halves. First, capture what you expect. Then read back what the public URL gives you. Our fictional worksheet concepts follow that shape. Each one is a scenario specification and is not offered as a downloadable product. <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-baseline-capture">Baseline Capture, a fictional worksheet for copy and canonical URL</a>, records expected copy and URL. The second worksheet, <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-public-readback">Public Readback, a fictional worksheet for published copy</a>, records the observed response and content.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>For the title, <a href="https://developers.google.com/search/docs/appearance/title-link">Google's title link guidance</a> recommends titles that are distinct, descriptive, concise and accurate about page content. A title can be present and still fail on accuracy. For the body, compare the observed text with the baseline copy.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>In practice, that means asking four questions of the observed title: is it distinct from other pages, does it describe this page, is it concise, and does it match what the page actually says? For the body, note each difference from the baseline text rather than only whether the page looks fine. Recording differences gives the reviewer something specific to act on, and it keeps the pass, fail or unknown result honest.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Casey's fictional workflow runs in this order: take the draft baseline, pick the expected public URL, run the checklist, record the result. A disposable <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/guide">demonstration guide page</a> gives a non-transactional example of the baseline, change, publish and verification workflow.</p>

<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Frequently asked questions</h2>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Does a 200 confirm the page content is correct?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>No. Per MDN, 200 indicates request success. It doesn't compare the delivered copy with an approved draft, so title and body need their own check.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Does the published perspective include unpublished changes?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>No. According to Sanity's documentation, the published perspective excludes unpublished changes. The drafts perspective applies drafts, which is what preview uses.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Why might a live page not show my latest draft edit?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Draft edits leave the published document unchanged until publication. If the public page serves the published document, it returns 200 with the older copy. When the frontend configuration isn't clear to you, record that as unknown.</p>
<h3 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What does a 301 do differently from a 200?</h3>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A 301 says the resource moved permanently and names the destination in the Location header, which the browser then requests. By contrast, a 200 serves content at the URL requested.</p>

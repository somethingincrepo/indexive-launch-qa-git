<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A synthetic publishing test can show that pipeline mechanics behaved as specified on controlled fixtures. It cannot show editorial quality, production behavior, search indexing, accessibility or any failure rate. By the Indexive QA editorial team, 2026-11-03. The byline is a test attribution for a collective label and does not name an individual expert.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The dataset is a controlled software QA run: 17 deterministic synthetic page-type fixtures pushed through a disposable GitHub repository and an isolated migrated database. All business names, personas and options in the scenario are fictional definitions dated 2026-11-02, with no purchases or contact submissions available.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What did the 17-fixture run establish?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>We ran 17 deterministic synthetic page-type fixtures through the registered implementation worker, an isolated migrated database and a disposable GitHub repository. Every fixture had persisted verification, a duplicate retry that left the provider SHA unchanged, and rollback with file absence and a public 404. The run receipt dated 2026-11-02 is the source for these results.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The sample is 17 software tests. It is not 17 customers and not 17 AI-written articles. The scenario businesses are fictional, as stated in the Northstar Demo Lab scenario specification, and nothing here is a commercial result.</p>

<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The table carries aggregate statements only. We publish no per-fixture rows, timings or rates, because the run summary does not support them.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Each row states an aggregate outcome from the receipt. The duplicate retry row says the provider SHA was unchanged for every fixture. Rollback is recorded as file absence and a public 404. The supplied summary does not provide an editorial assessment of the page copy, so these aggregate mechanics should not be presented as editorial-quality proof.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What the run does not establish</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Deterministic fixtures test delivery only. Nothing in the run measures whether a model writes good copy, and the run did not use the production worker. It also offers no search-indexing or accessibility proof.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The fixtures are synthetic software tests, so they cannot stand in for editorial work. A clean run is silent about whether copy is persuasive, accurate or useful to a reader. The same applies to the environment: an isolated migrated database and a disposable repository are controlled stand-ins, and the run does not show how the production worker would behave.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Seventeen passing runs cannot support a failure rate, an industry rate, a customer-impact estimate or statistical confidence. A run of 17 passes also says nothing about how often failure would occur in other runs or environments.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The supplied experiment receipts do not establish actual search-index status. Our test page is intentionally noindex,nofollow, and Google documents that a noindex rule can prevent indexing only when the crawler can access it (<a href="https://developers.google.com/search/docs/crawling-indexing/block-indexing">Google Search Central on blocking indexing</a>). Accessibility fares no better: the W3C describes its Easy Checks as preliminary, and passing them is not comprehensive conformance proof (<a href="https://www.w3.org/WAI/test-evaluate/preliminary/">W3C preliminary accessibility checks</a>).</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Why is an HTTP 200 not proof of correct published copy?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>An HTTP 200 means the request succeeded. MDN is explicit that a response status alone does not compare the delivered copy with an approved draft (<a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/200">MDN on HTTP 200</a>). A page can return 200 and still serve the wrong text.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Public readback closes that gap. The workflow we state on our test page is baseline, change, publish, public verification. You capture the expected copy and canonical URL first, then read the public page after publishing and compare observed response and content against the baseline. The fictional worksheet specifications cover each step: <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-baseline-capture">Publishing Review Baseline Capture: Copy and Canonical URL</a> records expected copy and URL, and <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-public-readback">Publishing Review Public Readback: Published Copy and Canonical URL</a> records the observed response and content. Both worksheets are scenario specifications only.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Does unchanged document text prove nothing was published?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>No. Sanity stores drafts, versions and published content as separate documents, with drafts carrying a drafts. ID prefix and published documents carrying none (<a href="https://www.sanity.io/docs/content-lake/drafts-and-versions">Sanity drafts and versions documentation</a>). The published perspective excludes unpublished changes, and later draft edits do not alter the published document until publication.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The same documentation notes that direct writes to the published document can also change it. So the current document text or updatedAt alone does not prove that publication never occurred (<a href="https://www.sanity.io/docs/content-lake/drafts-and-versions">Sanity documentation on state and timestamps</a>). Document state is one observation, and the public renderer is a separate one.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Delivery configuration adds a further caveat. A public frontend using the published perspective excludes draft-only edits, but an unknown frontend query or delivery setup must not be assumed to do so. Check what the frontend actually serves.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The same reasoning applies to preview. The drafts perspective applies drafts for preview, so a page that looks right in preview has shown you the draft view, not what the published perspective returns. Treat a preview check and a public readback as two separate records, and note which perspective each one used.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>In practice this means recording two separate observations. The first is document state: which document IDs exist, which carry the drafts. prefix, and what the published document contains. The second is public renderer output: what a reader would receive at the expected URL. If the two disagree, the disagreement is the finding. If you can only observe one of them, record the other as unknown rather than inferring it.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>How should duplicate retry and rollback be verified?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>In the run, every fixture had a duplicate retry without a provider SHA change, and the unchanged SHA was the check used for the retry. Rollback was recorded as file absence and a public 404. The receipts support these aggregate statements only. They give no per-fixture timings, no retry counts and no rates.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A reverted document alone is not enough evidence. The fictional <a href="https://scoring-spell-mailing-lenses.trycloudflare.com/qa-semantic-rollback-decision">Publishing Review Rollback Decision: Prior Copy and Canonical URL</a> worksheet specification records a reason, the prior revision and a post-restore check. It is a scenario specification, not a downloadable product, and it makes no claim about how any real rollback performs.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>The retry and rollback results are best read as the receipt states them. For the retry, the provider SHA was unchanged. For the rollback, the receipt records file absence and a public 404. The supplied summary establishes the stated retry and rollback observations, not an editorial-quality assessment. Keep these results separate from judgments about the content.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>How do you record pass, fail and unknown results?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>We use three states for each check. In the fictional scenario, an editor persona named Casey (not a real customer or expert) uses a draft baseline, selects an expected public URL, runs a checklist, and records pass, fail or unknown. Unresolved items go to a responsible reviewer.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Unknown deserves its own state because many checks cannot be answered from the evidence at hand, such as whether a frontend serves the published perspective. Recording it as pass hides the gap, and recording it as fail misstates it. The worksheets capture the supporting detail: expected copy, observed response and rollback reason.</p>

<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>How would you rerun this evaluation?</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Start with a written baseline for each fixture: the approved copy, the expected canonical URL and the page title. Fix these before publishing so the comparison cannot drift toward whatever the pipeline happened to deliver. The fictional Baseline Capture worksheet records expected copy and URL. Record any additional title criteria separately rather than attributing extra fields to that worksheet.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Next, publish the fixture and record the persisted verification result. Read the public page while it is present and compare it with the approved baseline. Check the title, visible content, structured data and canonical signals against the separately recorded criteria. Record pass, fail or unknown for each check; an unknown result needs follow-up rather than an assumed pass.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>After that public comparison, repeat the publish and compare the provider SHA before and after. Finally, roll back the new-file fixture and confirm the expected file absence and public 404. Do not attempt a copy comparison against a page that has already been removed. For a different rollback that restores an earlier page instead of removing a new one, record that expected prior revision and compare the restored public page against it. This distinguishes the observed new-file fixture result from a broader proposed rollback procedure.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Finally, state the scope of the result in the same place as the result. A rerun on 17 fixtures reproduces a software test. It does not reproduce a customer outcome, and the write-up should say so every time it is repeated. The scenario definitions are dated 2026-11-02 and the article date is 2026-11-03, and keeping both dates visible helps a later reader tell the fixture setup from the write-up.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Keep observation records separate from interpretation</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>A useful rerun report can give each check its own expected value, observed value and disposition. This is a procedural recommendation built from the fictional baseline and readback concepts, not an additional result from the original experiment. Record the expected copy and URL before the change. After publishing, record the response and content actually observed. For a retry, retain the before-and-after provider identifiers. For rollback, state whether the intended result is removal of a new page or restoration of a prior revision.</p>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Keep the interpretation alongside those observations. An unchanged provider SHA supports the stated retry check; it does not by itself establish editorial correctness or comprehensive accessibility. A public 404 after removing a new-file fixture supports that particular rollback expectation. It does not show that a different site restored its prior content correctly. If the relevant observation is unavailable, report unknown and identify the missing check rather than widening the claim beyond the receipt.</p>
<h2 style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>What the evidence justifies doing now</h2>
<p style={{"maxWidth":"100%","overflowWrap":"anywhere","boxSizing":"border-box"}}>Treat the run as evidence that the pipeline mechanics behaved as specified on fixtures, and nothing broader. Before wider claims, add real-run receipts, production worker testing, indexing observation and a full accessibility evaluation. A larger, varied sample would be needed before anyone discusses a rate.</p>
